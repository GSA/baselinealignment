# Validate a testing process against an expanding Framework

Use this workflow to assess the testing process and its use of SI/tools, not to certify an artifact from sample results. The Baseline remains the procedure authority; expected Framework outcomes are test-specific evidence and require review.

1. Pin the collection, Baseline, Framework source revision and case versions. Review the manifest, sample dependencies and case metadata before selecting execution inputs. A case listed in the repository is not evidence that this collection has executed or validated it.
2. Select available cases and record the exact procedures and scenarios they exercise. Keep document procedures and supplemental criteria with no published cases visible in the coverage inventory. Do not label those targets not-applicable merely because fixtures are absent.
3. Keep source records, expected outcomes, outcome-bearing names/titles/comments and evaluator rationale outside the independent candidate workspace. Use neutral copies with documented transformations only after verifying that their code behavior, relationships and dependencies remain equivalent. Serve Jekyll/Liquid-dependent cases through the appropriate build rather than assuming raw-file copies are faithful. Do not automate neutralization with a blind search-and-replace across executable identifiers.
4. Have the candidate execute its normal test process with the proposed skill/instructions. Record actual outcomes, observations and limitations. A capability-limited result can be honest but is not a completed correct classification.
5. Freeze candidate output. The evaluator compares the scoped results with reviewed expected pass/fail/not-applicable outcomes. Record matched, mismatched or not-compared separately from artifact test outcomes: a correctly reported content failure is a successful classification, not a passing artifact.
6. Investigate disagreements using evidence and authoritative procedures. Determine whether the cause is a flawed case/expectation, a mapping problem, incomplete instructions, tool behavior, fixture transformation or an environment difference. Correct the appropriate component and rerun without overwriting the initial record.
7. Report case counts, procedure/scenario coverage, expected-outcome diversity, unavailable cases, mismatches and human-review status. Never label a single score Baseline alignment. Every active Baseline procedure must still be incorporated in a process claiming alignment; available cases are only part of its evidence.
8. Add new cases through stable IDs, versions, provenance, dependency hashes, reviewed rationale and expected results in the evaluator set. Expand passing/failing/not-applicable and edge-case diversity where meaningful. Version corrected expectations and retain prior scoped results.

Publish reviewed instructions and available validation evidence incrementally, with draft/review status and known gaps. Do not wait for a permanently complete case corpus, and do not imply that publication makes unexecuted tests validated. Custom supplemental examples remain distinct from official Framework cases.
